# 販売を考えるときの参考メモ

**これは、決定ではありません。** 2026-11-03 の相談で出た内容を、参考として残したもの。
実際に販売が決まったときに、あらためて相談して決める。

お客様の名前・図面は、このリポジトリに入れない（リポジトリが公開のあいだは、とくに）。

## 前提（相談で出たこと）

- 売るのは、会社として。**システムだけを売り、中に保存されたデータは売らない**（まっさらな状態で渡す）
- サーバーは、クラウドに置く
- 設定は、売った先で行ってもらう。こちらが更新したときは、お客様のところにも反映させたい
- 同時に使う人は、多くて10人
- 作った図面は、ずっと保存する（案件は、完成品として残す。ロックの機能は、いまは要らない）

## すでに実装したこと（参考）

販売とは別に、容量を抑えるために決めて、実装したもの（変更履歴 `CHANGELOG.md` を参照）。

- スケッチ読み取りに使う写真・PDFは、サーバーに預けない（以前の分は、「保存」を押したときと、`photos:purge` で消える）
- 控え（バックアップ）は、毎日午前0時（日本時間）に作り、10日分残す。写真は入れない
  - 10日 ＝ 過去5年で最も長かった連休（法律上の祝日＋土日で5日、年末年始 12/29〜1/3 を含めて9日）＋1日
- 測定：1万件で、データ本体は約313MB（1件約31KB）。控え10日分で約3GB。図面一覧は、2000件で約0.09秒

## 配り方（方式A：完成パッケージを送る）の考え方

- お客様が GitHub を見ると、ソースコードを渡すことになるので、お客様向けには、**完成パッケージ（コンテナ）**を配る
- 更新は、**新しい版があることを知らせる → 管理者がボタンを押したときだけ入れ替える**。勝手には更新しない
  - コンテナを動かせるクラウドのサービスなら、「新しい版を取り込んで入れ替える」機能がクラウド側にあるので、アプリ側で作るものは少ない
  - 更新の前には、自動で控えを作る。うまくいかなければ、1つ前の版に戻せるようにする
  - 更新パッケージには、会社の署名を付ける（配信元が乗っ取られると、全部のお客様に被害が及ぶため）
- 保存の仕組みが SQLite（1つのファイル）なので、サーバーは1台。データの置き場は、電源を切っても消えないディスクにする
- 最初の管理者を作る画面（いまは、コマンドで登録している）が、お客様向けには要る

## AI（Claude）について

- **お客様が、自分の Anthropic のアカウントで API キーを取る。** 売る側がキーを持ち、お客様に使わせると、利用料が売る側の負担になり、使った量の記録も必要になる
- キーは、サーバーの設定（`.env`）にだけ置く。利用者の端末・ブラウザには配らない（これまでどおり）
- AI の読み取りの責任は、「読み取り結果を、人が確認する」前提のままでよい（確認画面は、すでにある）

## コードを調べて見つかった、販売前に直す候補

| 内容 | 場所 | 状況 |
|---|---|---|
| 図面の右下の社名が「株式会社フジエレックス」固定 | `packages/layout/src/svg.ts`（`COMPANY_NAME`）、デスクトップ版の設定 | **配信先の会社名にする** |
| 引込元の初期値が「中電柱：」（中国電力）固定 | `packages/knowledge/src/questions.ts` | **中国電力以外は、その電力会社の呼び方にする** |
| 質問の入力例に、実在しそうな電柱名「猪子山（分）81」 | 質問の入力例、音声のサンプル資料 | 中立の例に替える候補 |
| AI のモデル名がコードに固定（`claude-opus-5`） | `apps/server/src/analyze.ts`、`apikey.ts` | モデルが終了すると、読み取りが全員止まる。設定で変えられる形にする候補 |
| AI の利用量の記録・上限が無い | `apps/server` | お客様のキーを使う方式なら、優先度は下がる。保留 |
| 社内専用の資料・設定が、リポジトリに混ざっている | `docs/setup-memo.md`（利用者ID）、`docs/feedback.md`（経緯）、社内Mac用の自動起動の設定、社内のメールアドレスなど | **配信するときは、渡さない** |

**方針（案）：** 会社名と電力会社は、お客様ごとに別のプログラムを作らず、**設定の内容として入れる**。
配る前に聞いた内容を設定に書けば、全員に同じ完成パッケージを渡せる（更新も1つの版で足りる）。

**作らないと決めたもの：** 操作の記録（誰がいつ何をしたか）、全案件の書き出し。

**電力会社が変わると、電柱名のほかにも、変えるものがあるかもしれない。** 各社の違いは、実際に配信する会社が決まったときに、お手本の図面や決まりを見せてもらって、確認しながら進める（勝手に決めない）。

## 配る前に、お客様に確認しておくこと

1. 図面の右下に入れる会社名（表記のとおり）
2. 電力会社の名称と、電柱の呼び方（例：「中電柱」の部分）
3. Anthropic のアカウントを作って、API キーを取っていただくこと
4. 使う人数（最大10人の範囲か）
5. 使うクラウドの種類と、https の住所（ドメイン）
6. 管理者のIDの名前（パスワードは、お客様が決める）

## 販売が決まってから決めること（保留）

- 料金（買い切りか年額か）、保守・更新の費用、サポートの範囲、古い版の打ち切り
- 利用規約・個人情報の取り扱い（AI に送ることの説明と同意、保存場所、保存期間、消す手順、事故のときの連絡）
- 権利の所在・納品物の範囲・再販の禁止・保証の範囲（契約書）。弁護士・弁理士への相談が必要な項目を含む
- 製品名・商標（「zumen」「単線結線図作成」は一般的な言葉で、商標が取りにくい）。Claude/Anthropic の名前を使うときの表記ルールと、再販・組み込みの扱い（Anthropic の利用規約で確認）
- 使っている部品のライセンス一覧（デスクトップ版は、ブラウザ部品 Chromium の表示義務もある）
- 保存に使っている部品（`node:sqlite`）が、Node.js 側で「実験的」とされている点（安定した部品に替えるか、使う版を固定する）
- 配り方の細かい部分、更新の仕組み、死活監視、外国語画面（英・仏・中・韓）を出すかどうか
- お客様ごとの独自の質問・ルールを、標準の内容と分けて持つ仕組み（更新で消えないように）
- 出荷前の確認表（`pnpm check` と `pnpm selftest` を合格条件にする）
